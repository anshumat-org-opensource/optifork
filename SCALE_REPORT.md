## Phase 2 — fixes applied

- **Backend segfault under load (availability) — FIXED.** Root cause (profiled, not guessed): `GET /flags` returned raw SQLAlchemy ORM objects to FastAPI's encoder; under concurrency this segfaults the worker (SIGSEGV / exit 139, `OOMKilled=false`, memory flat). Isolation ruled out OOM, uvloop/httptools, and the asyncpg statement-cache/version. Fix: `crud.serialize_flag()` returns plain dicts (same shape). The scenario that reliably crashed (`MixedUser`) now runs with 0 failures. Regression test: `backend/test_flag_serialization.py`.
- **Flag-eval p99 — profiled; worker-config fix (absolute target deferred).** Serial eval floor is ~4–6 ms (incl. the exposure INSERT+COMMIT), so per-request work already meets the target; the p99 blowup under load is single-Uvicorn-worker queuing. Workers are now configurable via `API_WORKERS`. Measured 1x/2x/4x (FlagEvalUser u=120): 1w=634 rps/p50 180 ms, 2w=1043 rps/110 ms, 4w=1158 rps/85 ms (0 errors). Clean linear scaling to 5,000 rps @ p99<20 ms needs a dedicated 2-machine env (load-gen separate from the backend); on this laptop CPU is shared with the load generator + Postgres.
- **prod healthcheck** `/health/ready` → `/health` (the route didn't exist, so the prod frontend never started).
- **Server-side pagination — DONE.** `limit`/`offset` (clamped, default 100, max 500, stable order) on `/flags`, `/segments`, `/configs`, `/experiments/`, `/experiments/results`, and exposure reads. No endpoint returns an unbounded collection.
- **Flag search — DONE** (approved scope exception). `GET /flags?search=` (case-insensitive substring on name + description, paginated). Measured ~10-28 ms across 10K flags (< 200 ms).
- **No lost updates — DONE.** Optimistic concurrency on flag updates: a `version` column + atomic guarded `UPDATE`; `PUT /flags/{name}` with a stale `expected_version` gets 409. 40 simultaneous edits → exactly one won, 39 rejected.
- **Bucketing + config propagation + hot-path cleanup** — chi²=7.60 over 10M (uniform); no-cache propagation is immediate; removed debug `print()`s on the experiment path.

## Architectural decisions needed (await approval)

Per the ground rules, these are **not** built without sign-off; the plan + trade-offs are recorded here so a Phase 2 target can exit as *approved plan* rather than *passing test*.

### Last-known-good flag values when the backend/DB is down

- **Why it needs an architectural change:** evaluation is a server API call today; clients hold no local state, so if the backend or DB is unreachable, a call simply fails. Serving last-known values requires caching flag config **on the client side** — i.e. introducing a lightweight SDK (or a cached config snapshot endpoint + client that stores it). That is explicitly the 'move evaluation toward an SDK' change the ground rules say to stop and ask on.
- **Options & trade-offs:**
  1. **Client SDK with local cache + background refresh.** Clients fetch a config snapshot, evaluate locally, refresh every N seconds; serve the cached snapshot if refresh fails. Best resilience + removes per-eval latency, but is a real new component (biggest change).
  2. **Snapshot endpoint + thin cache in the existing server-call path** (e.g. a sidecar/edge cache). Smaller, but still adds a caching layer and a propagation story.
  3. **Do nothing** (accept that eval fails when the backend/DB is down). No change; target stays unmet and is recorded as a known limitation.
- **Recommendation:** decide between (1) and (3) based on whether local-eval resilience is in scope for this effort. Awaiting direction.

## Remaining known gaps (post Phase 2)

Still open after the Phase 2 fixes above:
- Exposure logging is a synchronous INSERT+COMMIT on every evaluation (write amplification) and exposure reads sort by an **unindexed `timestamp`** — not yet optimized (per-eval floor is still only ~4-6 ms, so not a current failure; revisit if it shows up at full scale).
- **No DB migrations** (`create_all` only) → schema changes (e.g. the new `version` column) need a fresh DB or a manual migration; existing SQLite files drift from the models.
- Optimistic concurrency implemented for **flags**; segments/configs still last-writer-wins (no reported requirement, but noted for symmetry).
- Last-known-good resilience is unbuilt pending the architectural decision above.
