## ⚠️ Backend availability under load — FAILED

The single-worker backend **became unavailable during the load run** and did not recover (Locust saw `RemoteDisconnected` → `ConnectionReset` → `ConnectionRefused`; later scenarios hit 100% connection-refused). Latency numbers for scenarios that ran after the backend went down are meaningless — they are recorded but flagged.

**Evidence / interpretation (not yet root-caused — that is Phase 2 work):** the backend container log ends abruptly after normal `200 OK` responses with **no Python traceback**, which is consistent with the process being **SIGKILL'd (OOM)** rather than raising an exception. Caveats before drawing conclusions: (a) the scale stack has **no backend memory limit** and the Docker host may have been under memory pressure from other containers running on this machine; (b) `FlagEvalUser` (pure reads+exposure writes) completed with **0 errors** and the backend died only during `MixedUser`, which adds the experiment-assign path. Phase 2 must profile memory under sustained load before attributing a cause. Re-running on an unloaded host and/or with a memory limit is the first step.

## Known gaps carried into Phase 2 (from FEATURES.md / findings)

- No server-side pagination on most list endpoints; no search endpoint.
- No optimistic concurrency/versioning → concurrent edits last-writer-wins.
- Exposure logging is a synchronous INSERT+COMMIT on every evaluation (write amplification).
- Exposure reads sort by an unindexed `timestamp`.
- Single Uvicorn worker; no caching; evaluation is server-API-only (no SDK).
- `docker-compose.prod.yml` backend healthcheck points at `/health/ready`, which does not exist (monitoring router disabled) — prod frontend would never start. Scale harness uses `docker-compose.scale.yml` with a working `/health` check.
- No DB migrations (`create_all` only) → existing SQLite files drift from the models.
- Debug `print()` statements on the hot path (experiment assign: `user_attributes`, `flag_result`, flag repr) spam stdout under load — Phase 2 cleanup.
- Backend became unavailable under mixed load (see above); needs memory profiling in Phase 2.
